Архитектура микросервисы почему именно они во первых я так звхотел во вторых удобсво масштобирования можно легко добавлять новые сервисы типо тг бота это удобно это нам надо дальше ппдробнее про сервисы 

сам по себе сервис маленькое независимое монолитное приложение можно его запустить отделно от всего приложения и он будет функционировать и выполнять свои задачи 
архитектура сервисов иденттична

**иии да мы нарушили DRY а точнее не нарушили а сознательно пренебреегли ради того чтобы полностью разделить контекст сервисов сделать из независимыми и еще мы нарушим  SRP потому что будем использовать SAGA сервис будет следить за своими оркестрацией и обеспечивать атомарность**

- main.py точка входа 
- api енпоинты
- buidnes бизенс логика он обычно называеться service но пофик 
- depends зависимости DI для ендпоинтов 
- schema схема запросов/ответов модели данных для серелизации/десереализации/валидации
- serializer серелиализаторы
- utils пррросто впомогателные функции 
- папка db вссе связанно с базой данных
- папака migrations управление миграциями (создание/удаление/модификация/контроль версий таблиц)
- папка rd это работа с редисом (у меня был какой то конфлик с библиотеками поэтому я придумал такое названи)
- папка rebbitmq брокер сообщений 

Сервис авторизаци 

отвечает как не сложно за авторизацию/аунтификацию пользователей уаправляет учетными данными токенами и сессиями используем классику жанра **JWT** горячо любимая технология скорость безопастность все классно только много места занимают нооо ресурсы мы не экономим самое главное удолетворить нашего клиента

отновные сущности
User - учетные данные почта пароль 
UserSession - сессия пользователя на устройстве хранит активность пользователя к ней привязываються токены точнеее они закрепляються за ней 


Сервис рецептов 

управляет профилем пользователя связями пользователь рецепт избранное лакнутое созданное и так далее 

основные сущьности 
Profile - профиль пользователя 
Recipe - рецепты 
Ingridients - сложно догодаться но это ингрдиенты 
RecipeIngridients - а вот это реально интересно табличка костыль ну мы не можем связать напрямю рецепты и ингредеенты или для каждого рецепта делать список ингридииентов нам нужно где то и как то хрнить уникалные данные для пары рецепт ингридеент например это грамовки 

окей с сервисами немного разобрались а как же их обьеденить и причем тут NGINX

да всеми сервисами управляет докер точнее он отвечает за их сборку монтирование и настроку среды взаимодействия выделяет им ресурсы он также поднимает нашу бд кеши и тд это все можно в **docker-compose**

а причем тут nginx он являеться api getway классический подход для микросервисов хотя в монолите тоже испоользуеться че такое api getway ну все серывисы работают на своих портах что нам для каждого домен покупать нет кончечно вот мы их обьеленяем получаеться из внешней сети досткпен только nginx а все общение сервисов происходит внури dokcer сети именно nginx решает приватный ли маршрут и в какой сервис пойдет запрос подробнее можно посмотреть в **nginx.conf**
